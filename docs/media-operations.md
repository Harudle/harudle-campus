# 음성 서비스 운영 준비

운영 관리 모드는 LiveKit → Daily → Cloudflare 순서로 사용합니다. 서버의 예약 한도에 도달하거나 제공자를 사용할 수 없으면 기존 음성 연결을 정리한 뒤 다음 제공자로 전환합니다. 세 제공자를 모두 사용할 수 없으면 새 연결을 막습니다. Daily와 Cloudflare는 무료량 초과 시 서버의 추정과 별도로 청구될 수 있습니다.

LiveKit 프로젝트가 Build 요금제인지 운영자가 계속 확인해야 합니다. 프로젝트를 유료 요금제로 바꾸면 이 코드가 요금제 변경을 자동으로 감지하지 못합니다. EC2와 다른 AWS 서비스의 비용도 이 제한에 포함되지 않습니다.

## 지금 준비된 동작

운영과 로컬 시험에서 서버는 LiveKit, Daily, Cloudflare 순서로 연결합니다. 각 연결 전에 예상 사용량을 예약하고, 한도에 도달하면 이전 연결을 서버에서 정리한 뒤 다음 서비스로 전환합니다. 정리가 확인되지 않으면 전환을 멈춥니다. SQLite에 현재 제공자, 예약량과 정리 대상이 남아 서버 재시작 뒤에도 이어서 확인합니다. Cloudflare까지 사용할 수 없으면 중단합니다. 전환할 때 음성이 잠시 끊기며, 화면 공유는 다시 선택해야 할 수 있습니다.

예약량은 35일 동안 유지합니다. 제공사별 청구일이 달라도 이전 예약을 곧바로 지우지 않기 위한 보수적인 방법입니다. 허용된 서비스를 다 사용해 중단된 경우, 오래된 예약이 보관 기간을 지나고 연결 상태 확인이 성공하면 다시 연결할 수 있습니다. 현재 서비스가 동작 중일 때 더 앞 순서 서비스로 즉시 돌아가지는 않습니다.

이전 LiveKit 단독 정책에서 이미 중단된 상태로 배포해도 DB를 초기화할 필요가 없습니다. 연결 정리가 끝나고 다음 제공자의 예약 여유와 상태 확인이 성공하면 주기적인 복구 검사에서 Daily로 재개합니다. 기존 예약량은 그대로 유지합니다.

Daily는 최대 연결 시간에 60초를 더하고 LiveKit은 30초를 더 예약합니다. LiveKit은 참가자 수를 기준으로 수신 전송량도 예상하여 예약합니다. Cloudflare는 수신별 예상 전송량에 정리 지연을 위한 시간을 더 예약합니다. 실제 이용량과 같지 않습니다. 다른 앱의 계정 사용량이나 예상보다 큰 전송량을 모두 통제하지는 못합니다.

Cloudflare 시험 구성은 EC2와 별도의 Worker 및 Durable Object에 세션과 종료 시간을 기록합니다. EC2가 꺼져 있는 동안에도 시간이 되면 트랙 종료를 시도합니다. 결과가 불확실하거나 Cloudflare API에 접근하지 못하면 다시 시도합니다. Workers Free의 요청 한도, Cloudflare 장애, 네트워크 지연이 있으면 즉시 종료되지 않을 수 있습니다. 따라서 이것도 청구 상한이 아닙니다. Workers 요금제가 Paid로 바뀌면 별도 요금이 생길 수 있습니다.

## 운영 전에 해결할 문제

1. Daily와 Cloudflare는 등록된 결제수단에 과금될 수 있습니다. 제공사가 강제하는 지출 상한이 없으므로 서버 제한만으로 0원을 보장할 수 없습니다. 계정 전체의 사용량과 다른 앱의 사용 여부도 확인해야 합니다.
2. LiveKit은 시간과 전송량을 예상해 예약하지만 실제 사용량을 이 코드가 계속 조회하지는 않습니다. 변조된 클라이언트, 다른 앱 또는 네트워크 재전송량은 예상과 다를 수 있습니다. 제공사의 실제 한도에 도달한 뒤 모든 오류 상황에서 전환이 성공한다고 보장하지 않습니다.
3. 초기 DB에 넣는 기존 사용량은 같은 계정의 이전 35일 사용량을 포함해야 합니다. 조회가 불완전하면 0으로 넣지 않습니다. 이후에도 다른 앱이 같은 계정을 사용하면 기록이 모자랄 수 있습니다. Cloudflare 분석은 최근 31일과 오늘을 조회하며, 조회 기간이 부족하거나 오류가 나면 연결을 막습니다. 표본과 반영 지연 때문에 청구 금액과 다를 수 있습니다.
4. 응답을 잃은 Daily 방 생성이나 Cloudflare 작업은 나중에 완료될 수 있습니다. 이런 경우 기록이 남고 서비스가 중단될 수 있습니다. 제공사에서 상태를 확인하고 해결하는 절차를 먼저 마련해야 합니다.
5. 운영 회의 목록은 서버를 다시 시작해도 유지되지만 24시간 후 만료됩니다. 사용자 인증과 초대 관리가 없고 위치는 브라우저에서 보낸 값이므로 운영용 비공개 대화의 안전을 보장하지 않습니다.
6. 두 물리 컴퓨터, 실제 마이크, 실제 화면에서 전환과 화면 글씨 가독성을 추가 시험해야 합니다. 사용자 수와 장시간 사용도 시험해야 합니다.

2026년 11월 9일 Cloudflare 시험에서 정리 확인이 남은 세션 기록 세 개를 발견했습니다. 두 개는 트랙이 없다고 조회되었지만 요청 완료가 불확실하고, 한 개는 조회가 시간 초과됐습니다. 시험 브라우저와 서버는 닫았지만 제공사 확인이 되기 전까지 완료로 표시하지 않습니다. 추적 정보는 Git에서 제외된 `.env.cloudflare-test-recovery.local`과 별도 시험 DB에 보관했습니다. 운영 초기값을 계산할 때 이 시험의 예약량도 포함해야 합니다.

같은 Cloudflare 앱을 운영에 사용할 때는 서버를 멈춘 상태에서 `scripts/import-cloudflare-recovery.mjs`로 이 기록을 운영 DB에 가져옵니다. `MEDIA_LEGACY_STATE_PATH`는 기존 DB, `MEDIA_STATE_PATH`는 운영 DB를 가리켜야 하며, 같은 앱임을 확인한 경우에만 `MEDIA_LEGACY_SAME_APP_CONFIRMED=1`을 설정합니다. 운영 DB의 Cloudflare 초기 사용량이 이전 시험의 전체 예약량보다 작으면 가져오지 않습니다. 미확인 기록이 남은 동안 LiveKit과 Daily는 사용할 수 있지만 Cloudflare 새 연결은 막습니다. 서버가 주기적으로 다시 확인하고 정리가 확인되면 Cloudflare를 다시 사용할 수 있습니다.

Daily와 Cloudflare에도 새로 연결하므로 세 제공자의 키, 예약 한도, Cloudflare 사용량 조회와 별도 종료 Worker를 모두 준비해야 합니다. `MEDIA_TEST_FREE_ONLY=1`은 LiveKit만 사용하는 시험용 제한입니다. 운영에서 세 제공자를 사용하려면 이 값을 설정하지 않습니다.

## 이 컴퓨터에서 다시 시험하기

이번 시험 계정의 설정과 사용량 DB는 Git에 포함되지 않는 `.env.*` 파일에만 보관합니다. 서버가 꺼졌다면 저장소 폴더에서 `bash scripts/run-local-media-demo.sh`를 실행합니다. 다음으로 `http://127.0.0.1:18092/?nomock`을 엽니다. 이 주소는 서버를 실행한 컴퓨터에서만 열립니다. 시험 사용량 한도는 작게 잡았으므로 사용 중 제공자가 바뀌거나 연결이 중단될 수 있습니다.

회의실에 들어가면 회의를 공개 또는 비공개로 만들 수 있습니다. 비공개 회의는 8자 이상의 비밀번호를 입력해야 합니다. 같은 회의를 선택해야 음성, 화면과 근처 채팅을 함께 주고받을 수 있습니다. 전체 채팅은 회의와 관계없이 모두에게 보입니다.

시험 DB의 기존 사용량은 확인한 기록보다 크게 잡은 추정값입니다. 계정의 모든 과거 사용량을 청구서와 대조한 값은 아닙니다. 이 파일을 삭제하거나 다시 만들면 예약 기록이 사라지므로 그러지 않습니다. 운영 초기값으로도 사용하지 않습니다.

## EC2에 필요한 설정

키는 브라우저가 아니라 EC2의 서버 환경에 넣습니다. LiveKit URL과 API 키 및 시크릿, Daily 도메인과 API 키, Cloudflare SFU 앱 ID 및 시크릿, Cloudflare 분석 조회 토큰, 별도 Worker 주소와 인증 토큰이 필요합니다. Worker에는 EC2용 인증 토큰과 SFU 앱 ID 및 시크릿을 비밀값으로 따로 설정합니다. 저장소나 프런트엔드 코드에 실제 값을 넣지 않습니다.

별도 운영 계정이나 앱을 만들면 시험과 운영의 사용량을 구분하기 쉽습니다. Cloudflare 계정에서 발급한 분석 및 청구 조회 토큰은 2026년 12월 9일에 만료됩니다. 만료되면 확인이 실패하여 Cloudflare 연결이 중단됩니다. 운영 전 재발급과 교체 절차가 필요합니다.

한 대의 EC2와 로컬 영구 디스크만 지원합니다. SQLite 파일뿐 아니라 WAL 파일도 같은 디스크에 유지해야 합니다. 무중단 교체 중 두 워커는 관리자 권한을 동시에 갖지 않으며, 이전 워커가 정리된 뒤 새 워커가 이어받습니다. 디스크 유실은 지원하지 않습니다. SQLite의 백업 기능이나 서버를 안전하게 멈춘 뒤의 일관된 백업을 사용해야 합니다.

`node:sqlite`를 사용하는 이 구성은 Node.js 22.13 이상이 필요합니다. `deploy/media-systemd.conf.example`은 systemd가 `/etc/harudle-campus/media.env`를 읽고 `/var/lib/harudle-campus`를 만들도록 하는 예시입니다. 이 파일은 자동 적용되지 않습니다. 환경 파일은 root만 읽도록 권한을 제한하고, 가능하면 EC2 역할과 AWS Systems Manager Parameter Store의 SecureString 또는 Secrets Manager로 비밀을 관리합니다.

운영에는 `MEDIA_PROVIDER=managed-draft`, `MEDIA_SINGLE_HOST=1`, `MEDIA_MEETINGS=persistent`, `MEDIA_STATE_PATH`와 `CAMPUS_PUBLIC_ORIGIN=https://campus.harudle.com`이 필요합니다. `CAMPUS_TRUST_PROXY=1`은 신뢰할 수 있는 로컬 Caddy가 앞에 있을 때만 설정합니다. 음성 연결은 동시에 최대 20명이고, 같은 IP의 토큰 요청은 기본적으로 분당 12회까지입니다. 이 제한과 웹소켓 출처 검사는 무단 사용을 완전히 막지 않으며, 특히 같은 계정의 다른 앱 사용량을 막지 못합니다.

운영 DB는 `scripts/media-state-init.mjs`로 한 번만 만듭니다. `MEDIA_STATE_PATH`는 절대 경로여야 하고, 기존 파일은 덮어쓰지 않습니다. 다음 값은 실제 계정 기록과 운영 정책을 확인한 후 모두 명시해야 합니다.

- `MEDIA_LIVEKIT_LIMIT_SECONDS`, `MEDIA_LIVEKIT_BASELINE_SECONDS`
- `MEDIA_LIVEKIT_LIMIT_BYTES`, `MEDIA_LIVEKIT_BASELINE_BYTES`
- `MEDIA_DAILY_LIMIT_SECONDS`, `MEDIA_DAILY_BASELINE_SECONDS`
- `MEDIA_CLOUDFLARE_LIMIT_BYTES`, `MEDIA_CLOUDFLARE_BASELINE_BYTES`
- `MEDIA_STATE_BASELINE_CONFIRMED=1`

Cloudflare의 분석 기준 `CLOUDFLARE_BUDGET_BYTES`도 따로 설정합니다. 초기 입력값, 계정 전체 사용량과 여유분을 확인하기 전에는 초기화하거나 기능을 켜지 않습니다. 기존 DB를 삭제하고 다시 만들면 사용량 기록이 사라지므로, 단순 재시작 방법으로 사용하면 안 됩니다. 구 버전 DB가 있다면 서버를 멈추고 LiveKit 전송량 초기값을 확인한 뒤 `scripts/media-state-upgrade.mjs`로 보존하면서 올립니다.

검증 명령은 `npm test`, `npm run build`, `npm run check`입니다. 실제 결제 위험과 다른 컴퓨터의 통화 품질을 이 명령만으로 검증할 수는 없습니다.

서버에서 `MEDIA_STATE_PATH`를 지정해 `node scripts/media-status.mjs`를 실행하면 예약량, 현재 서비스, 정리할 연결 수를 볼 수 있습니다. 예약량은 청구 금액이 아니므로 제공사 청구 내역도 함께 확인해야 합니다.
